## Steps

### Step 1: تأكّد من توفّر الوصول

```
gh auth status && gh run list --workflow=daily_screener.yml --limit 3
```

نجح ⇒ تابع. فشل ⇒ **STOP** وأبلغ المالك أن التحقيق يحتاج وصولًا (أو أن يلصق هو
لقطة من صفحة Actions).

### Step 2: اجمع آخر 20 تشغيلة مجدولة

استخرج لكل تشغيلة **بحدث `schedule` فقط** (استبعد `workflow_dispatch`):

| الحقل | المصدر | المعنى |
|-------|--------|--------|
| `createdAt` | `gh run list --json` | لحظة استحقاق الكرون |
| `startedAt` | نفسه | لحظة بدء الجوب فعلًا |
| `updatedAt` | نفسه | لحظة الانتهاء |
| `conclusion` | نفسه | success / failure |

احسب لكل تشغيلة:
- `delay_min = startedAt - createdAt` (تأخّر GitHub)
- `duration_min = updatedAt - startedAt` (زمن التنفيذ)

⚠️ **افصل تشغيلات كرون التجديد `7 22 * * 5` عن اليومي `54 4 * * 2-5`** — مسارهما
مختلف تمامًا (`run_weekly_renewal` مقابل `run_daily_watchlist`) وخلطهما يفسد الوسيط.
حقل `event` وحده لا يميّزهما؛ استعمل ساعة `createdAt` (04:5x مقابل 22:0x UTC).

**Verify**: جدول من ~20 صفًّا، مقسوم إلى مجموعتين، بلا صفّ ناقص الأزمنة.

### Step 3: استخرج لحظة إرسال التقرير من السجلّ

`duration_min` يقيس الجوب كلّه (بما فيه `git_save` بعد الرسالة). المطلوب أدقّ:
**لحظة `send_telegram(msg)`** في السطر 11242.

لثلاث تشغيلات يومية على الأقل (الأحدث)، اسحب السجلّ:
```
gh run view <id> --log > /tmp/run_<id>.log
```
ثم استخرج طوابع الوقت. `log()` (`Super_stock.py:554-556`) يطبع
`[HH:MM:SS] <msg>` بتوقيت **الرنر (UTC)**. علامات مفيدة بالترتيب:

- `بدء الفحص — الوضع: FULL` → بداية `main`
- `حجم كون ناسداك بعد الفلترة: N سهم` → انتهاء `get_universe`
- `تحميل دفعة n/N` → مسار التحميل
- `بيانات صالحة لـ N سهم` → انتهاء `download_history`
- `الفرز: N مرشح مؤهّل` → انتهاء `scan_market`
- `انتهى الفحص ✅` → نهاية `main`

⚠️ **لا يوجد سطر سجلّ عند الإرسال نفسه.** فقدّر لحظة الإرسال بأنها بين آخر سطر قبلها
وأول سطر بعدها، **وصرّح بأنها تقدير محصور بين طابعين** — لا تخترع رقمًا.

**Verify**: لكل تشغيلة: `startedAt` UTC · طابع «الفرز: N مرشح» · طابع «انتهى الفحص» ·
نافذة الإرسال المقدَّرة.

arrival_ksa   = arrival_utc + 3 ساعات

احسب **الوسيط والمدى** لـ`arrival_ksa` عبر التشغيلات.

**Verify**: رقم وسيط + مدى + مقارنة صريحة.

### Step 5: اكتب `plans/012-findings.md`

أقسام إلزامية:

1. **الحكم في سطر واحد**: هل يصل التقرير داخل النافذة المدّعاة؟ نعم / لا / العيّنة لا تكفي.
2. **الأرقام**: جدول التشغيلات · وسيط ومدى `delay_min` · وسيط ومدى `duration_min` ·
   وسيط ومدى `arrival_ksa`.
3. **تفكيك الزمن**: كم من `duration` في التحميل مقابل التحليل مقابل الإثراء (من طوابع
   الخطوة 3).
4. **حدود الصدق** — إلزامية بأسلوب المستودع:
   - لحظة الإرسال **مقدَّرة بين طابعين** لا مقاسة.
   - العيّنة = آخر N تشغيلة فقط، وقد تشمل أيامًا كان فيها ياهو مخنوقًا.
   - `updatedAt` يشمل ما بعد الرسالة (`git_save` · تلغرام إضافي).
   - أي تشغيلة فاشلة استُبعدت (اذكر كم).
5. **خيارات للمالك** — **وصفية بلا توصية بالتنفيذ**، كلٌّ بتكلفته ومخاطره:
   - **(أ)** تقديم الكرون بمقدار `delay + duration` الوسيطَين (أبسط · لا يمسّ كودًا ·
     يجعل البدء ليليًّا وقد يقرأ إغلاقًا أقدم).
   - **(ب)** فصل الرسالة عن الفرز: إرسال تقرير المتابعة (يعتمد القائمة القائمة فقط)
     **قبل** الفرز الكامل، وإرسال «الجديد» بعده (يغيّر بنية الرسائل — يخالف عقد
     «لا قناة رابعة بلا طلب المالك» فيحتاج إذنًا صريحًا).
   - **(ج)** تقليص زمن الفرز (مثلًا `CHUNK_SLEEP`) — **⚠️ يمسّ احترام حدود ياهو
     وقد يُنزل التغطية تحت `DATA_HEALTH_MIN_PCT=85`؛ الأخطر في الثلاثة.**
6. **الشرط لأي خطوة تالية**: لا تُنفَّذ إلا بعد اختيار المالك صراحةً.

**Verify**: الملف موجود وفيه الأقسام الستّة.
