# PHASE 4 — PRE-REGISTRATION (written and merged before any Phase 4 number · 2026-10-08)

Mission: «FORENSIC PHASE 4 — PRE-REGISTERED CAUSAL TEST: FIRST TOUCH → ATTENTION/FOCUS/WATCH → RETEST → TRIGGER/ENTRY vs TWO-TOUCH AS AN EARLY CANDIDATE GATE». Research only. No production, V4, protocol, Telegram, three-condition, threshold, ranking or live-methodology change. No V5 / READY_NOW_V2 / production temporal engine / production state machine / replacement gate. No agents (project rule). Lookahead firewall as in §⑤. If any definition below must change, `PHASE4_AMENDMENT.md` records old / new / reason / timestamp / affected experiments — nothing changes silently.

## ① Hypotheses (fixed now) and what falsifies each
| H | Claim | Falsified if (any) |
|---|---|---|
| H0 | the current order is correct: Two-Touch belongs at candidate generation | Second Touch (production definition, §③-E2) occurs **after** the first defensible Faisal state in ≥ 60% of evaluable cases in BOTH discovery and validation sets, AND the current architecture A holds no object for the name on that date in ≥ 60% of those cases |
| H1 | Two-Touch is one of several candidate features; moving it later is not necessary | MOVE-LATER architectures (B/C/D) represent ≥ 2× more Faisal first-state rows than A **while** their observation-stage false-positive rate on matched negative controls is ≤ REMOVE's, in both sets |
| H2 | First Touch is a chart event with no Faisal-state significance | P(documented Faisal state within 20 sessions \| First Touch present on an identity-eligible name) ≥ 2× the same probability with First Touch absent, in the probe universe (§⑦-F1), AND First Touch precedes the first defensible Faisal state in ≥ 60% of evaluable cases |
| H3 | First Touch creates Focus/Watch opportunity but the second touch is not the decisive transition | Second Touch (either definition) precedes READY or ENTRY in ≥ 60% of the evaluable READY/ENTRY rows AND it is absent before FOCUS/WATCH in ≥ 60% of those rows (i.e. it sits specifically between Watch and Ready/Entry) |
| H4 | First Touch → observation/state → later retest/second touch is the correct temporal architecture | First Touch occurs AFTER the first defensible Faisal state in ≥ 50% of evaluable cases; OR Second Touch occurs BEFORE the first defensible Faisal state in ≥ 50%; OR MOVE-LATER represents fewer Faisal rows than REMOVE by > 20% of the restored count; OR the effect disappears on the validation set (validation represented share < half the discovery share); OR negative controls show the same observation→retest→trigger sequence at the same rate as positives (ratio < 1.5); OR the result holds only when DKI/SXTC/HUBC are included |
| H5 | the apparent order is an evidence artifact (dates, missing posts, retrospective labels, selection, survivorship, leakage, chart reconstruction) | ordering results change class (EXPECTED ↔ CONTRADICTED) for ≥ 30% of cases when (a) ambiguous-date rows (weekend/holiday mapping, month-precision) are dropped, or (b) INFERRED/WATCHLIST evidence is excluded and only DIRECT_TEXT/DIRECT_CHART/ACTION remain, or (c) when the lookahead check (§⑤) finds any row whose event date uses bars ≥ decision date |
| H6 | the architecture is real but depends on another missing feature before/after the retest | H4 survives but MOVE-LATER's matched-stage alignment at READY/ENTRY is < 50% while its observation alignment is ≥ 70% (the retest alone does not explain readiness) |

Decision rule: a hypothesis survives only if its falsifiers do not fire **and** the result replicates on the frozen validation set (§⑧). Level 5 only if all of §⑪ A–G hold. Otherwise the maximum is Level 4 and the report says «LEVEL 5 NOT ESTABLISHED».

## ② State definitions (Faisal side — from evidence dated ≤ the decision date only)
Observation classes as in Phase 3 (`fm_forensics/phase3/FAISAL_TIMELINE.csv`, `p3lib.classify`): MENTION · FOCUS · WATCH · READY · ENTRY · EXIT · UNKNOWN. MENTION never establishes a state. Evidence class per unit (§6 of the brief), mapped from the timeline fields: TELEGRAM/X_POST with decision text → **DIRECT_TEXT**; CHART_IMAGE → **DIRECT_CHART**; a reply/thread with the owner → **CONVERSATION**; ENTRY/EXIT words («دخلت» «طلعت» position text) → **ACTION**; APP_SCREENSHOT list (`X_20260918_23`) → **WATCHLIST**; a ticker with ≥ 2 dated FOCUS/WATCH days → additionally **REPEATED_ATTENTION**; anything else → **INFERRED** or **UNKNOWN**. Only DIRECT_TEXT / DIRECT_CHART / CONVERSATION / ACTION / WATCHLIST establish a strong state; INFERRED never does. First Touch is **not** assumed to be Focus or Watch; Second Touch is **not** assumed to be Trigger or Entry — these are measured (§⑥).
- FIRST_DEFENSIBLE_FAISAL_STATE_DATE = earliest dated FOCUS/WATCH/READY/ENTRY unit for the ticker (session-mapped: weekend/holiday → next session, flagged `DATE_AMBIGUOUS=1`).
- FIRST_READY_DATE / FIRST_ENTRY_DATE = earliest dated READY / ENTRY unit. FAISAL_TRIGGER_TEXT_DATE = earliest dated unit whose text names the trigger as happened («سحب» / «ثبات» after a test) — recorded separately from the bot-computable trigger below; absent → UNKNOWN.

## ③ Event definitions (bot side — computed from bars strictly before the decision date; production code unmodified)
All on the provider-adjusted daily bars of `fm_forensics/data/bars_2026-10-08.json.gz` (the Phase 2/3 probe set, 232 symbols).
- **E0 LEVEL(T)** = min(Low) over the last 30 bars before T (`Super_stock.tested_level` base: `df.tail(30)["Low"].min()`).
- **E1 FIRST TOUCH** of LEVEL(T) = the session whose Low equals LEVEL(T) (first occurrence inside the 30-bar window). Observable from the next session (the bar has closed). `FIRST_TOUCH_DATE` is that session; `SESSIONS_SINCE_FIRST_TOUCH(T)` = number of sessions from it to T (= `bars_since_low30` in `p3lib.context`). A new lower Low inside the window re-defines LEVEL and resets E1.
- **E2 SECOND TOUCH (production)** = first session T′ ≥ FIRST_TOUCH_DATE + 1 at which `tested_level(bars < T′, lookback 30, tol 0.015, min_touches 2)` returns `touches ≥ 2` with `level == LEVEL` (same level to 4 dp): at least one more bar whose Low is within 1.5% of LEVEL and is not adjacent to the first-touch cluster (production cluster rule). This is exactly the production anchor gate's pass condition for that level. Invalidated if a Low < LEVEL × (1 − 0.015) occurs first (then LEVEL changes) — note: a Faisal-style sweep of 7–13% below the low **necessarily** invalidates E2 (new 30-bar min); this consequence is itself a test (§⑥-O4).
- **E3 RETEST (Faisal lifecycle, production display function `pivot_cycle_state`, window 60)** = first session at which `pivot_cycle_state(bars < T′)` reports `stage ≥ 3` with `bottom == LEVEL` (±1e-4): a bounce ≥ 10% (`METHOD_BOUNCE_MIN_PCT`) from the bottom followed by a Low back inside `METHOD_HOLD_TOL`=1.5% above the bottom (branch `hold`) or below it down to `PIVOT_SWEEP_PCT`=13% (branch `sweep`). Deeper than 13% = bottom broken (new cycle). If `pivot_cycle_state`'s bottom differs from LEVEL (its window is 60 bars), the row records `LEVEL_MISMATCH=1` and E3 is taken on its own bottom.
- **E4 TRIGGER (bot-computable proxy of Faisal's documented trigger, `TG_57872` two branches)** = the earlier of (a) E3 with branch `sweep` and the first close back above LEVEL after the sweep low (sweep-and-reclaim), or (b) `pivot_cycle_state.stage == 4` (held ≥ `STABILITY_MIN`=3 sessions after the test without touching the band again). Recorded with `TRIGGER_BRANCH`.
- **E5 BREAK / INVALIDATION** = first Low < LEVEL × (1 − 0.13) or 60 sessions after FIRST_TOUCH without E3 (the production cycle window). Observation objects (§④) end at E5.
- **ENTRY** = documented Faisal ENTRY only (no bot entry exists).
Every ledger row carries `DECISION_DATE` (T), `DATA_CUTOFF` (bars < T), `EVIDENCE_CUTOFF` (Faisal units dated ≤ T), `FUTURE_REVEAL_DATE` (the date after which forward events were read; forward events are written only to columns whose names start with `FWD_`).
Tolerances and windows are the production constants read by name at run time (`tol 0.015`, `lookback 30`, `min_touches 2`, `METHOD_BOUNCE_MIN_PCT 10`, `METHOD_HOLD_TOL 0.015`, `PIVOT_SWEEP_PCT 13`, `STABILITY_MIN 3`, `PIVOT_CYCLE_WIN 60`); **none is tuned**.

## ④ Research architectures (same data, same features, no threshold change — replay only)
Identity-eligibility on a date = Phase 3 `p3lib.run_gates(sym, bars<T, neutral=("ANCHOR",))` returns PASS (every production gate except the two-touch anchor).
- **A (current)**: CANDIDATE(T) = production `run_gates` PASS (anchor included). States: candidate → (watchlist) → READY NOW. No pre-candidate object.
- **REMOVE**: CANDIDATE(T) = identity-eligible (anchor neutralised). Same stage as A's candidate.
- **B (First Touch → candidate/observation; Second Touch → watch/ready)**: OBSERVATION(T) = identity-eligible on some session s ∈ [FIRST_TOUCH_DATE+1, T] for the current LEVEL and E5 not yet reached (a persisting object); WATCH/READY(T) = OBSERVATION ∧ E2 occurred ≤ T.
- **C (First Touch → focus/watch; Second Touch → ready/trigger)**: FOCUS/WATCH(T) as B's OBSERVATION; READY/TRIGGER(T) = OBSERVATION ∧ (E2 ≤ T **or** E3 ≤ T) — the retest in Faisal's broader sense counts.
- **D (First Touch → observation; Second Touch → trigger; entry separate)**: OBSERVATION as B; TRIGGER(T) = OBSERVATION ∧ E4 ≤ T; ENTRY not modelled (none exists in the bot).
Memory is bounded by the structure (E5), not by a tuned N.

## ⑤ Lookahead rules
For every row: states and events from bars < T and Faisal units dated ≤ T only. Forward events (E2/E3/E4/E5 after T, outcomes) are computed after the historical columns are frozen and written to `FWD_*` columns with `FUTURE_REVEAL_DATE`. Weekend/holiday Faisal dates map to the next session (`p3lib.session`) and are flagged. Bot watchlist/READY snapshots = last commit ≤ T (Phase 3 rule). Replay thresholds are today's live envelope (stated limitation, unchanged from Phase 3). An automated check (`p4lib.lookahead_audit`) asserts for every ledger row that `max(bar date used) < DECISION_DATE`; any violation invalidates the row and is listed in `DATA_AVAILABILITY_AUDIT.csv`.

## ⑥ Measures (fixed now)
- **O1 ordering per ticker** (`PHASE_ORDERING_MATRIX.csv`): FIRST_TOUCH_DATE (of LEVEL at the first-state date) vs FIRST_STATE_DATE vs SECOND_TOUCH_DATE (E2; forward-revealed if after) vs TRIGGER_DATE (E4; forward) vs ENTRY_DATE (documented). ORDER_RESULT = EXPECTED if FIRST_TOUCH ≤ FIRST_STATE < SECOND_TOUCH/RETEST (where these exist) and TRIGGER ≤ ENTRY (where both exist); CONTRADICTED if any evaluable pair is reversed; INSUFFICIENT if the needed dates are missing. EVIDENCE_QUALITY = DIRECT_TEXT/DIRECT_CHART/CONVERSATION/ACTION/WATCHLIST/REPEATED_ATTENTION/INFERRED.
- **O2 First Touch → attention** (`FIRST_TOUCH_ANALYSIS.csv`): sessions from FIRST_TOUCH to first FOCUS, WATCH, READY, ENTRY (documented only): median, IQR, min, max, n, unknown n; proportion positive / zero / negative. H4 weakened if negative ≥ 50%.
- **O3 Second Touch role** (`SECOND_TOUCH_ANALYSIS.csv`, `TEMPORAL_ROLE_ANALYSIS.csv`): for E2 and E3 separately, position relative to each of FOCUS, WATCH, READY, TRIGGER(text), ENTRY: BEFORE / SAME / AFTER / NEVER (within 60 sessions) / UNKNOWN, with counts per set.
- **O4 sweep-vs-anchor exclusivity**: share of Faisal cases whose documented or bot-computed retest is a sweep (E3 branch `sweep` or text «سحب») — each such case is one where E2 (production) can never pass on that level.
- **O5 architecture comparison** (`ARCHITECTURE_COMPARISON.csv`, `STATE_ALIGNMENT_MATRIX.csv`): for A / REMOVE / B / C / D on every Faisal dated row and on every matched-control day: object present at any stage (recall), object at the matched stage (FOCUS/WATCH ↔ observation or candidate; READY ↔ B watch/ready, C ready, D observation-with-E3; ENTRY ↔ D trigger), first divergence per ticker (first dated Faisal row with no object), false positives = share of control-days with an object at the observation stage and at the ready/trigger stage, transition timing = sessions between the architecture's stage change and Faisal's dated transition where both exist. Components reported separately; no weighted score.
- **O6 MOVE vs REMOVE** (`MOVE_VS_REMOVE_RESULTS.csv`): Faisal rows represented (any stage) and at matched stage; control-days flagged at the *alert* stage (A candidate / REMOVE candidate / B watch-ready / C ready / D trigger) and at the observation stage. «MOVE preserves recall with less alert-stage noise» = MOVE's any-stage recall ≥ 80% of REMOVE's recall AND MOVE's alert-stage control rate ≤ A's × 1.5. Pre-registered expectation stated honestly: observation-stage noise of MOVE equals REMOVE's by construction (same eligibility set); the question is whether the *alert* stage stays clean while the object exists earlier.
- **O7 First-Touch / Second-Touch feature tests** (§18-19, diagnostic only): in the probe universe on identity-eligible symbol-days, P(documented Faisal FOCUS/WATCH/READY/ENTRY within 20 sessions \| First Touch within the last 5 sessions) vs (\| no First Touch in the last 5 sessions); P(READY/ENTRY within 20 \| E2 or E3 present) vs absent. Denominators printed; no threshold derived.
- **O8 lead-time distributions** (§20): First Touch → Focus/Watch/Ready/Entry; Second Touch (E2, E3) → Ready/Trigger(text)/Entry; median, IQR, min, max, n, unknown n; documented vs bot-computed kept apart.
- **O9 transitions** (§21): Focus→Watch, Watch→Ready, Ready→Trigger, Trigger→Entry: directly supported / inferred / n independent cases / can occur without the preceding state / second-touch position → CONFIRMED / MODIFIED / REJECTED / UNKNOWN.
- **O10 data availability** (`DATA_AVAILABILITY_AUDIT.csv`): per event type: in bot data? at the right timestamp? timeframe? history depth? without future adjustment? → DATA MISSING / MODEL MISSING / STATE MODEL MISSING.
- **O11 gate stage audit** (`PHASE4_GATE_STAGE_MATRIX.csv`): every gate before the anchor: concept, current stage, evidence stage (EARLY / LATER / BOTH / UNKNOWN), direct support, contradictions, keep/move/unknown, confidence.

- **Matched negative controls** (built before any architecture result): for each Faisal ticker's first-state date D, candidates = non-Faisal symbols in the probe set that are identity-eligible (anchor neutralised) on D with ≥ 120 bars; matched on price bucket (<1 / 1–5 / >5), ATR14% bucket (<8 / 8–15 / >15), 20-session dollar-volume bucket (<50k / 50k–500k / >500k), reverse split within 252 bars (yes/no); nearest in (log price, atr, log dollar-vol) up to 4 per positive, no symbol reused across positives where avoidable; seed 20261008. They are «technically similar names on the same date where Faisal did not progress» (no dated Faisal unit at all for the symbol).
- **F1 probe universe** for §18-19: all 232 symbols × sessions from 2025-06-20 on which identity-eligibility is computed (reuse of Phase 3 `bot_states` + a NO_ANCHOR pass).
- Faisal rows with month-precision dates or no bars are excluded (counted).

## ⑧ Blind validation protocol
1. Build the ledger and all architectures for the discovery set and the matched controls; write results.
2. Freeze: commit the discovery results.
3. Run the identical code on the validation set; write results; no definition, tolerance, state mapping or ordering rule may change. If validation fails, the report says so; no rescue.

## ⑨ Statistical reporting
Counts with denominators; medians/IQR; proportions with Wilson 95% intervals where n ≥ 5; ratios positive/negative with both denominators. No p-values are promised; no thresholds derived.

## ⑩ Predictions (scored in the final report)
P1 First Touch precedes the first defensible Faisal state in ≥ 70% of evaluable cases (both sets). P2 Production Second Touch (E2) has **not** occurred by the first Faisal state in ≥ 70% of evaluable cases. P3 E2 never occurs within 60 sessions for ≥ 30% of Faisal levels (sweeps and higher second supports invalidate it). P4 MOVE-LATER (B/C/D) any-stage recall ≥ 80% of REMOVE's recall with alert-stage control rate ≤ A's × 1.5. P5 The validation set reproduces P1-P2 within 20 points of the discovery set. P6 Second Touch (E2 or E3) position relative to READY/ENTRY is mixed (not ≥ 70% either side) — i.e. the second touch is a confirmation in Faisal's text but his dated READY calls often precede it. Failed predictions are published.

## ⑪ Level 5 criteria (all required)
A direct/strong Faisal evidence supports the ordering · B First/Second-Touch ordering replicates across independent Faisal cases (discovery) · C validation reproduces it · D matched negative controls do not reproduce the same behaviour (ratio ≥ 1.5 on the observation→retest→trigger sequence) · E MOVE-LATER materially better than REMOVE alone (§⑥-O6 rule) · F no lookahead contamination (automated check) · G no anchor-specific tuning (anchors excluded from all rule counts). Any failure ⇒ «LEVEL 5 NOT ESTABLISHED».
